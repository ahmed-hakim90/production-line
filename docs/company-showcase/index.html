المشكلة التي يحلها النظام

قبل ForgeOps: بيانات متناثرة، أرقام إنتاج غير موثوقة، تضارب بين الأقسام، وصلاحيات غير منضبطة.

تشغيل يومي حقيقي

ليس نظام تقارير فقط — خطط، أوامر شغل، صرف مواد، تحويلات، جرد، وتحصيل.

مساران متوازيان

تصنيع في المصنع + صيانة في المراكز، مع تموين قطع غيار وخزينة وفواتير.

عزل الشركات

كل شركة لها مسار /t/{slug}/ وبيانات معزولة — نفس المنصة لعدة مستأجرين.

المسار التشغيلي الأساسي

من الكتالوج إلى التكلفة الشهرية — مع مسار صيانة موازٍ.

كتالوج + BOM← خطة إنتاج← صرف للإنتاج← تقرير يومي← مخزون / تحويلات← تكلفة شهرية

مسار الصيانة الموازي: استلام → تشخيص → تقدير → موافقة عميل → إصلاح/قطع → تحصيل → تسليم.

هندسة البيانات — باختصار

الداتا مش متناثرة: كل موديول يملك كيانه، والمسارات الحساسة تثبت على السيرفر.

مصدر حقيقة واحد

Firestore لكل شركة (tenantId). الإنتاج لا يغيّر الرصيد؛ المخازن تملك الحركات؛ الصيانة تملك الطلب.

حماية الكتابة

صرف/تحويلات الإنتاج الحساسة عبر Cloud Functions. الواجهة تُظهر الصلاحيات؛ القواعد والـ Functions تمنع التجاوز.

قوائم محدودة لا مسح أعمى

الشاشات التشغيلية تعمل بفلاتر وحدود صفحات. التقارير الثقيلة تعتمد ملخصات — مش فتح كل التاريخ في المتصفح.

يستحمل لحد فين؟

تقييم سعة موجّه للإدارة — الحجم المستهدف مريح على Firebase؛ العنق الحقيقي هو نمط التحميل لا عدد الصفوف.
