1) هندسة البيانات — من يملك الحقيقة؟

النظام مش «ملفات على جهاز». كل عملية تشغيلية ترجع لمصدر بيانات واحد مع حدود واضحة بين الموديولات.

الطبقات

  • الواجهة (React) — تعرض، تجمع إدخال، وتظهر حالات التحميل/الخطأ.
  • الخدمات / الـ Store — تنسّق القراءة والكتابة للموديول.
  • Firestore — مستندات بعزل tenantId + فهارس مركّبة للفلاتر.
  • Cloud Functions — ترحيل مخزون حساس، عمليات لا يجب الوثوق فيها من المتصفح.
  • Rules + Permissions — القواعد على السيرفر هي حد الأمان؛ صلاحيات الواجهة للـ UX فقط.

قواعد ملكية الدومين

  • الإنتاج يملك الخطط والتقارير — لا يغيّر الأرصدة مباشرة.
  • المخازن تملك الحركات والأرصدة — أي صرف/تحويل يمر من مسارها.
  • الصيانة تملك الطلب والحالة والتشخيص — طلب القطع يتحول لإذن مخزون.
  • العملاء سجل ماستر — الطلبات تشير بـ customerId بدل تكرار الاسم.
  • التكاليف/الحسابات تقرأ كميات التشغيل وتحسب — لا تعيد اختراع الإنتاج.
مثال تدفّق آمن: تقرير إنتاج → طلب صرف → اعتماد/تجهيز → حركة مخزون على Functions → طباعة. الواجهة لا «تخترع» رصيدًا؛ السيرفر يثبت الحركة.

2) كيف بتتعامل المنصة مع الداتا يوميًا؟

نوع الداتاطريقة التعاملليش مهم للشركة؟
بيانات رئيسية (منتجات، مواد، عملاء، موظفين) مستندات Firestore لكل كيان + صلاحيات عرض/تعديل مصدر واحد بدل نسخ Excel متعددة
تشغيل يومي (تقارير، طلبات صيانة، تحويلات) قوائم مفلترة + حدود صفحات + شارات معلّقة الشاشة تفضل سريعة حتى مع تراكم الشهور
حركات مالية/مخزنية حساسة Cloud Functions + تحقق tenant + صلاحية سيرفر يمنع التلاعب من المتصفح وتضارب الرصيد
حضور وبصمة سجلات خام + ملخصات؛ استيراد على دفعات (~400) يستوعب سحب يومي/شهري بدون قفل النظام
تقارير وتكلفة شهرية تجميعات/ملخصات بدل مسح كل التاريخ في المتصفح تكلفة قراءة أقل وقرار أسرع لنهاية الشهر
ملفات وطباعة Storage بمسارات company/{tenantId}/... + قوالب طباعة عزل ملفات الشركة ومشاركة واتساب/PDF آمنة نسبيًا

3) يستحمل لحد فين؟ — غلاف السعة

الأرقام التالية هي الحجم التشغيلي المستهدف الذي تم تقييمه على البنية الحالية (Firestore + Auth + Functions). ليست «سقف Firebase»، بل ما نوصي بالاعتماد عليه بثقة مع ممارسات القراءة الصحيحة.

البندالحجم المستهدفتقييم السعةملاحظة عملية
أصناف / منتجات ~7,000 مريح لـ Firebase المهم: عدم تحميل الكتالوج كاملًا في كل جلسة دخول
عملاء ~8,000 مريح لـ Firebase موديول العملاء موجود؛ البحث والتصفح بالصفحات أهم من العدد
مستخدمون نشطون معًا ~100 مريح جدًا مناسب لمصنع + عدة مراكز صيانة في نفس الشركة
موظفين (HR) مئات–آلاف مناسب بيئة حالية تظهر مئات السجلات مع فلاتر وبحث
شغل يومي (قراءة/كتابة مستمرة) كثيف ممكن بشرط modeling فهارس + حدود قوائم + ملخصات KPI
فواتير / تحصيل صيانة متوسط–عالٍ داخل مسار الإصلاح يعمل بحذر المسارات المالية الأفضل تظل server-owned عند التزامن العالي
تقارير تحليلية ثقيلة جدًا شهور طويلة / كل التاريخ ليس عبر مسح كامل من الواجهة الملخصات أو تصدير BI — مش فتح مليون صف في المتصفح

4) إجابة مباشرة للإدارة

نعم — تعتمد على المنصة لهذا الحجم

  • 7 آلاف صنف + 8 آلاف عميل + 100 يوزر = حجم صغير نسبيًا على Firestore.
  • تصنيع + مخازن + صيانة + HR + جودة تعمل كمسارات يومية حقيقية.
  • عزل الشركات يسمح بنفس المنصة لأكثر من مستأجر بدون خلط بيانات.
  • الحركات الحساسة للمخزون جزء كبير منها محصّن على السيرفر.

لكن — الحدود ليست «عدد الصفوف»

  • تحميل بيانات رئيسية كاملة عند كل Login يرفع التكلفة ويبطئ الإقلاع.
  • التقارير الثقيلة بدون ملخصات ترفع فاتورة القراءات.
  • الكتابات المالية المتزامنة الكثيفة تحتاج عدّادات/مسارات سيرفر محكمة.
  • سحب بصمة ضخم يجب أن يمر من مسار واحد مضبوط (دفعات + dedupe + tenant).
الخلاصة للإدارة: النظام يستوعب تشغيل مصنع + شبكة مراكز بالحجم أعلاه. التوسّع الأكبر (آلاف المستخدمين المتزامنين، فوترة بيع عامة كثيفة جدًا، تحليلات تاريخية ضخمة) يحتاج نفس المنصة مع تحسينات قراءة كسولة وملخصات وتشديد مسارات السيرفر — مش تغيير المنتج من الصفر.

السيناريوالسلوك المتوقعالحد العملي

6) حماية واتساق — مش بس سرعة

عزل الشركات

المسار /t/{slug} + tenantId على المستندات. مستخدم شركة لا يدخل بيانات شركة أخرى.

صلاحيات دقيقة

مصفوفة عرض/إضافة/تعديل/حذف لكل مورد. الواجهة تُخفي؛ السيرفر يمنع.

سجل وموافقات

عمليات حرجة تمر بموافقة (تحويلات، صرف، سلف، مدفوعات) مع إمكانية التدقيق.

7) خارطة نمو موصى بها (باختصار)
