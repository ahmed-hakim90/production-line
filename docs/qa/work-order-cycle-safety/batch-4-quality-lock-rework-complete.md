# الدفعة الرابعة — قفل الجودة وإعادة التشغيل (٢٠٢٦-٠٩-١٣)

## ما تم بناؤه

**قفل الجودة** (`lockQuality` / `unlockQuality`، صلاحية مدير الجودة):
- القفل خاص بالأمر بالكامل. إن كانت هناك ساعة "قيد الإنتاج" فعليًا، يوقفها القفل فورًا بسجل توقف مصدره `quality_lock` (متمايز عن توقف المشرف العادي `production`).
- إن كانت الساعة متوقفة بالفعل بسبب مستقل من المشرف، لا يُنشئ القفل سجل توقف جديدًا — يكتفي بتفعيل `qualityHold` فقط، فيبقى السبب الأصلي للتوقف محفوظًا كما هو.
- فك القفل يستأنف الساعة تلقائيًا **فقط** إذا كان توقفها الحالي مصدره القفل نفسه (`source == quality_lock`)؛ أي توقف مستقل يبقى متوقفًا وينتظر استئنافًا يدويًا من المشرف.
- بدء الساعة والإرسال والاستئناف كلها محظورة أثناء القفل (فحص خادمي، لا إخفاء واجهة فقط). سبب القفل إلزامي، ويُحفظ سجل `quality_holds` لكل قفل/فك قفل، وإشعار يُكتب مباشرة في مجموعة `notifications` الموجودة أصلًا (يظهر في جرس الإشعارات الحالي للمشرف دون بناء نظام إشعارات جديد).

**قرار المرفوض وإعادة التشغيل** (`decideRejectedDisposition` / `submitRework` / `claimReworkInspection` / `submitReworkQualityReport` / `approveReworkQualityReport`):
- بعد اعتماد أي نتيجة فحص فيها مرفوض، يظهر لمدير الجودة قرار وحيد غير قابل للتكرار: تقسيم المرفوض بين "إعادة تشغيل" و"هالك نهائي"، بسبب إلزامي.
- إعادة التشغيل تُنشئ مهمة مستقلة (`rework_attempts`) مرتبطة بنفس الحاوية الأصلية، رقم محاولة تسلسلي، ومهمتها الخاصة لمشرف الإنتاج — منفصلة تمامًا عن جدول الساعات.
- ناتج إعادة التشغيل **لا يُضاف إلى `producedQuantity`** إطلاقًا (ليست إنتاجًا جديدًا)، ولا يمكن أن يتجاوز الكمية المرسلة للتشغيل.
- المحاولة تمر بنفس مسار الفحص (حجز حصري، مشاركات، اعتماد) قبل أن تُضاف نتيجتها المقبولة لـ`approvedAcceptedQuantity` — **مرة واحدة فقط**، بفحص خادمي يمنع الاعتماد المكرر.
- لو أسفرت محاولة إعادة التشغيل نفسها عن مرفوض، يمكن لمدير الجودة اتخاذ قرار تصرف جديد عليها (نفس الإجراء، مطبّق بشكل عام على أي حاوية أو محاولة) — دون كود إضافي.

## التحقق

**اختبار آلي جديد** (`tests/work-order-cycle-quality-lock-rework.integration.ts`، ضمن `npm run test:work-order-cycle`) يغطي:
- قفل أثناء ساعة تعمل → توقف فوري بمصدر `quality_lock` → فك القفل يستأنفها تلقائيًا.
- قفل فوق توقف مستقل موجود مسبقًا → لا سجل توقف مكرر → فك القفل **لا** يستأنفها؛ المشرف يستأنفها يدويًا بنجاح بعد فك القفل.
- قفل بلا ساعة جارية → لا عطل، بدء الساعة محظور أثناء القفل فقط، ولا بدء تلقائي بعد فك القفل.
- تقسيم مرفوض ١٠٠ وحدة (٨٠ مقبول/٢٠ مرفوض) إلى ١٢ إعادة تشغيل و٨ هالك، رفض مجموع لا يساوي المرفوض، رفض تكرار القرار، رفض تسجيل ناتج يتجاوز ١٢، ورفض اعتماد مكرر لنفس المحاولة.

**تجربة حية كاملة بأربعة حسابات حقيقية** على أمر تجريبي (`B4-LOCK-REWORK`، ٥٠ وحدة):
1. قفلت الجودة أثناء توقف مستقل سبق أن سجّله المشرف بسببه الخاص — تأكدت عبر REST مباشرة من وجود سجل توقف واحد فقط بمصدر `production` (لم يُستبدل). فك القفل لم يستأنف الساعة (بقيت متوقفة)، ثم استأنفها المشرف يدويًا بنجاح.
2. سجّل المشرف إنتاج ٥٠، فحص مراقب واحد الكل: ٤٠ مقبول و١٠ مرفوض. اعتمد مدير الجودة (`المقبول المعتمد` صفر ← ٤٠).
3. قسّم مدير الجودة المرفوض ١٠ إلى ٦ إعادة تشغيل و٤ هالك نهائي. ظهرت مهمة "إعادة تشغيل رقم ١ — ٦ وحدة" فورًا لمشرف الإنتاج.
4. سجّل المشرف ناتج إعادة التشغيل ٥ من ٦ (فَقْد وحدة أثناء إعادة التشغيل) — تأكدت أن `المنتج المسجل` بقي ٥٠ ولم يتحول لـ٥٥.
5. فحص مراقب ثانٍ محاولة إعادة التشغيل بالكامل: ٥ مقبول، ٠ مرفوض. اعتمد مدير الجودة.
6. **النتيجة النهائية: `المقبول المعتمد للهدف` = ٤٥ بالضبط (٤٠ + ٥)، و`المنتج المسجل` ظل ٥٠** — مطابقة تامة للكميات، بلا أي تكرار في الإنتاج أو الاعتماد.

هذا يطابق حرفيًا شرط قبول الدفعة الرابعة في طلبكم: **"تجربة قفل مع توقف مستقل، وفك القفل، وإعادة تشغيل وفحص واعتماد، مع تطابق الكميات وعدم تكرار الإنتاج."**

## خلل وُجد وأُصلح أثناء التحقق نفسه

بعد إضافة حقل `reworkAttempts` لدالة القراءة، نسيت إعادة بناء الخادم (`npm --prefix functions run build`) قبل الاختبار الحي، فظهرت مهمة إعادة التشغيل في قاعدة البيانات لكن لم تظهر في الواجهة. اكتشفته بفحص استدعاء الدالة مباشرة عبر curl (قارنت الاستجابة الفعلية بالمتوقع)، لا بتخمين. بعد إعادة البناء ظهرت فورًا وصحّت التجربة الحية بالكامل. هذا تحديدًا سبب عدم اعتباري بناء TypeScript دليلًا كافيًا — الدليل الوحيد المعتمد هنا هو تشغيل حقيقي وفحص الاستجابة الفعلية.

## ما تبقى مفتوحًا

- الربط مع التغليف (استهلاك `approvedAcceptedQuantity` النهائي شاملًا مقبول إعادة التشغيل) خارج نطاق هذه الدفعة، يأتي في دفعة التغليف والمخزن.
- لم أختبر تعدد مستويات إعادة التشغيل (محاولة ثانية على مرفوض محاولة أولى) ميدانيًا في الواجهة — الكود يدعمه عبر نفس الإجراءات (مختبر بنيويًا فقط، غير مجرَّب حيًّا).
- الهالك النهائي (`scrapQuantity`) يُسجَّل كرقم في قرار التصرف فقط؛ لا حركة مخزون أو تسجيل هالك مادي مرتبط به بعد — ينتظر دفعة التخزين إن كان مطلوبًا.
