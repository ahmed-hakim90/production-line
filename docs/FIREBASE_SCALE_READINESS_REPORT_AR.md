# تقرير جاهزية Firebase للحجم التشغيلي

**التاريخ:** 2026-08-03  
**النطاق:** تقييم قدرة البنية الحالية (Firestore + Auth + Functions + Storage) على تحمّل تقريبًا:

| العنصر | الحجم المستهدف |
|--------|----------------|
| أصناف / منتجات | ~7,000 |
| عملاء | ~8,000 |
| مستخدمون نشطون | ~100 |
| شغل يومي | كثيف (قراءة/كتابة مستمرة) |
| فواتير | عند التفعيل الكامل |
| موارد بشرية + سحب بصمة | تشغيل يومي |

**الخلاصة التنفيذية:**  
Firebase **يتحمّل الحجم الرقمي** (7 آلاف صنف / 8 آلاف عميل / 100 يوزر) بسهولة من ناحية السعة.  
الجاهزية الحالية للنظام **مش كاملة** بسبب طريقة التحميل والصلاحيات ومسارات الفواتير/البصمة، مش بسبب حدود Firebase نفسها.

| الحكم | النتيجة |
|-------|---------|
| سعة Firebase الخام | ✅ كافية |
| جاهزية المشروع الحالي لنفس الحجم | ⚠️ مش جاهز بالكامل بدون تعديلات P0 |
| فواتير بيع عامة + CRM عملاء | ❌ غير موجودة كمنتج جاهز (موجود مسار إصلاح فقط) |
| HR + حضور/بصمة | ✅ موجودة، لكن مسار السحب يحتاج hardening |

---

## 1) سياق النظام الحالي

المشروع ERP مصنعي متعدد المستأجرين (multi-tenant):

- Frontend: React + Zustand + Firebase SDK
- قاعدة البيانات: Cloud Firestore (`tenantId` على المستندات)
- Auth: Firebase Auth + أدوار في `roles` / `users`
- Server: Cloud Functions لمسارات مخزون حساسة وتجميعات محدودة
- Offline/PWA: كاش محلي محدود (single-tab)

الموديولات الموجودة فعليًا: إنتاج، مخزون، HR، حضور/ZKTeco، صيانة/إصلاح، جودة، تكاليف.  
**لا يوجد** موديول CRM عملاء مستقل، ولا فواتير بيع عامة خارج مسار قطع غيار الإصلاح.

---

## 2) هل الأرقام كبيرة على Firebase؟

| السيناريو | تقييم السعة |
|-----------|-------------|
| 7,000 منتج | صغير لـ Firestore |
| 8,000 عميل | صغير لـ Firestore |
| 100 مستخدم نشط | مريح جدًا |
| آلاف القراءات/الكتابات اليومية | ممكن، بشرط modeling وقراءة جزئية |
| تقارير شهرية ثقيلة | تحتاج ملخصات جاهزة / BigQuery وليس scan كامل |

**الخلاصة:** المشكلة ليست “عدد الصفوف”، بل **كيف بنقرأ ونكتب**.

## 3) تقييم المجالات المطلوبة

### 3.1 الأصناف (~7,000)

**الوضع:** مجموعة `products` موجودة وتعمل.  
**المخاطر الحالية:**

1. عند تسجيل الدخول يتم تحميل كل المنتجات عبر `productService.getAll()` داخل `_loadAppData` (`store/useAppStore.ts`).
2. مع 100 مستخدم، كل جلسة جديدة تعيد قراءة الكتالوج كاملًا → ضغط reads + ذاكرة متصفح + بطء cold start.
3. ملاحظات الأداء توثّق أن تقسيم الـ bootstrap ما زال مؤجلًا (`docs/PERFORMANCE_NOTES.md`).

**الحكم:** Firebase يتحملها. التطبيق الحالي **هيتعب** لو فضلت سياسة “حمّل الكل عند الدخول”.

### 3.2 العملاء (~8,000)

**الوضع:** لا يوجد `modules/customers/` ولا مجموعة CRM أولى المستوى.  
العميل اليوم غالبًا حقول منصوصة على أوامر/فواتير الإصلاح (`customerName` / `customerPhone`).

**الحكم:** لا يمكن “اعتماد” النظام الحالي لـ 8,000 عميل ككيان تشغيلي بدون بناء موديول عملاء + فهارس بحث + pagination.

### 3.3 المستخدمون (~100)

**الوضع:** مناسب. Auth + roles + tenant isolation موجودة.  
Presence/heartbeat موجودان ومقيدة بالـ tenant.

**الحكم:** ✅ مناسب للحجم.

### 3.4 الفواتير

**الموجود:**
- فواتير بيع قطع غيار الإصلاح: `repair_sales_invoices`
- إنشاء الفاتورة من الكلاينت مع آثار جانبية على المخزون والخزينة

**المخاطر:**
1. تسلسل غير ذري: فاتورة → تعديل مخزون → خزينة (احتمال فشل جزئي تحت الضغط).
2. `nextInvoiceNo()` يقرأ آخر 200 فاتورة بدون `tenantQuery` ويحسب الرقم التالي — عرضة للتصادم بين مستأجرين/مستخدمين متزامنين.
3. `list()` لبعض المسارات غير مقيد دائمًا بـ tenant.

**غير الموجود:**
- فواتير مبيعات عامة / POS / حسابات مدينة كاملة (OMS موثّق كـ greenfield ملغى/مؤجل).

**الحكم:** مسار الإصلاح ينفع بحذر لحجم متوسط. الفوترة اليومية الثقيلة العامة تحتاج Callable + عدّاد تسلسلي transactional.

### 3.5 المخزون والحركات اليومية

**نقاط قوة:**
- ADR-002 نقل جزء من ترحيل مخزون الإنتاج/المستهلكات إلى Cloud Functions.
- فهارس مركّبة كثيرة على حركات المخزون.
- ملخصات يومية/فترية موجودة جزئيًا.

**نقاط ضعف:**
- حركات يدوية ومسار قطع غيار الإصلاح ما زالا من الكلاينت.
- بعض مؤشرات KPI تعتمد page-scan بحد أعلى — إما تكلفة قراءة عالية أو truncation صامت.

**الحكم:** ⚠️ جاهزية جزئية. المسارات الحساسة يجب أن تكون server-owned بالكامل قبل الاعتماد لحمل يومي كبير.

### 3.6 HR والرواتب

**الموجود:** موظفون، أقسام، ورديات، إجازات، قروض، رواتب، ملخصات حضور شهرية.  
**المخاطر:** محرك الرواتب يعمل من الكلاينت (`payrollEngine`) — تحت تزامن HR قد يحدث تعارض تكلفة/اتساق.

**الحكم:** ✅ للتشغيل الحالي المتوسط. ⚠️ يُفضّل نقل generate/finalize إلى Functions قبل نمو أكبر.

### 3.7 سحب البصمة (ZKTeco)

**الموجود:**
- استيراد Excel/CSV، watch folder، gateway payload
- تخزين: `attendance_raw_logs` / `attendance_records` / summaries
- كتابة على دفعات بحجم 400 (`WRITE_CHUNK`)

**المخاطر:**
1. لا يوجد Cloud Function لسحب الجهاز مباشرة؛ المسار من المتصفح/gateway → Firestore.
2. `getLogsByDateRange` يفلتر بالتاريخ فقط بدون `tenantId` — خطر عزل/تكلفة.
3. dumps كبيرة للحضور ترفع reads/writes بسرعة لو اتعملت من جلسات متعددة.

**الحكم:** التخزين ينفع. مسار السحب يحتاج hardening (server ingest + tenant filter + dedupe + quota).

## 4) الأمن والصلاحيات (أثر مباشر على الاعتماد)

### نقاط قوة
- عزل tenant على مسارات كثيرة.
- صلاحيات دقيقة على payroll وبعض مسارات المخزون/الإصلاح.
- `isSuperAdmin` مقفول من تعديل الكلاينت في القواعد.

### مخاطر عالية
1. **Catch-all rules** لمجموعات ERP (`products`, `employees`, `attendance_*`, …): أي مستخدم نشط بنفس الـ tenant يمكنه create/update/delete بدون permission key دقيق.
2. **`pl_sameTenantOrLegacyRead`**: يسمح بقراءة مستندات قديمة بلا `tenantId` إلى أن يكتمل الـ backfill.
3. صلاحيات الواجهة (`utils/permissions.ts`) للـ UX فقط وليست حدود أمان.

**أثر الحجم:** مع 100 مستخدم، اتساع سطح الهجوم أكبر؛ حساب مخترق واحد يمكنه العبث ببيانات رئيسية واسعة تحت القواعد الحالية.

## 5) التكلفة والأداء المتوقع (تقريبي)

افتراضات: 100 مستخدم، جلسة يومية، كتالوج 7k منتج، تحميل كامل عند الدخول.

| البند | تقدير أثر |
|-------|-----------|
| قراءة صف منتجات لكل login | ~7,000 read × عدد مرات فتح النظام يوميًا |
| نفس النمط للموظفين/الخطط/أوامر الشغل | يضاعف التكلفة ووقت الإقلاع |
| استيراد بصمة شهري كبير | آلاف–عشرات الآلاف writes دفعة واحدة (مقبول لو مرة/يوم من مسار واحد) |
| تقارير بدون ملخصات | أعلى مصدر تكلفة طويل الأمد |

Firebase يتحمّل؛ **الفاتورة الشهرية** هي اللي هتتأثر لو فضلنا full-collection loads.

## 6) مصفوفة الجاهزية

| المتطلب | Firebase خام | النظام الحالي | قرار |
|---------|--------------|---------------|------|
| 7,000 صنف | ✅ | ⚠️ bootstrap كامل | يصلح بعد lazy load |
| 8,000 عميل | ✅ | ❌ لا يوجد CRM | يحتاج بناء موديول |
| 100 يوزر أكشن/داتا | ✅ | ⚠️ قواعد عامة واسعة | يصلح مع تضييق rules |
| شغل يومي كبير | ✅ | ⚠️ قراءات زائدة + client writes | يحتاج تحسين modeling |
| فواتير عامة | ✅ | ❌/جزئي (إصلاح فقط) | يحتاج تصميم server-owned |
| HR | ✅ | ✅ مع تحفظ الرواتب | جاهز نسبيًا |
| سحب بصمة | ✅ كتخزين | ⚠️ ingest من الكلاينت | يحتاج backend/gateway محصّن |

## 7) خطة عمل موصى بها (حسب الأولوية)

### P0 — قبل الاعتماد التشغيلي على الحجم المذكور
1. إيقاف تحميل الكتالوج/الموظفين كاملًا عند الدخول؛ تحميل كسول حسب الصفحة + pagination/بحث.
2. تحديد نطاق المنتج: إن كانت الفواتير العامة مطلوبة، اعتبر CRM + Sales مسار greenfield ولا تمدّد فواتير الإصلاح.
3. نقل إنشاء فاتورة الإصلاح + آثار المخزون/الخزينة إلى Callable (نفس فلسفة ADR-002) مع عدّاد `invoiceNo` transactional لكل tenant.
4. تضييق catch-all في `firestore.rules` ليتطلب permissions حقيقية على الكتابة/الحذف للمجموعات الحساسة.
5. إصلاح استعلامات الحضور لتشمل دائمًا `tenantId`، ونقل ingest البصمة لمسار سيرفر/بوابة موثوقة مع dedupe.

### P1 — استقرار يومي وتكلفة
6. عدم استخدام `getAll` لفحص تفرد الأكواد؛ استخدم counters/claims.
7. ملخصات يومية جاهزة للمخزون/الحضور/الفواتير بدل page scans.
8. إنهاء backfill لـ `tenantId` ثم إزالة legacy read من القواعد.
9. اختبارات حمل: login مع 7k منتج، فواتير متزامنة، استيراد بصمة شهري، 100 presence.

### P2 — تقوية تشغيلية
10. نقل payroll generate/finalize إلى Functions.
11. تقسيم `useAppStore` لشرائح دومين وتقليل الاشتراكات العامة.
12. طبقة تقارير/BI (BigQuery export أو scheduled aggregates) للشغل التحليلي الثقيل.

---

## 8) الإجابة المباشرة على السؤال

> هل أقدر أعتمد على Firebase لحد 7000 صنف و 8000 عميل و 100 يوزر وشغل يومي كبير وفواتير و HR وسحب بصمة؟

**نعم تعتمد على Firebase كمنصة.**  
**لكن اعتماد النظام الحالي “كما هو” على كل السيناريو دفعة واحدة: لا.**

- للتصنيع + HR + مخزون + حضور بالحجم ده: قريب من الجاهزية بعد إغلاق بنود P0.
- للعملاء 8 آلاف + فواتير بيع عامة كثيفة: يحتاج بناء/تحصين واضح قبل الإطلاق.
- عنق الزجاجة المتوقع: bootstrap الكامل + كتابات مالية/مخزنية من الكلاينت + قواعد عامة واسعة + ingest البصمة، وليس سقف Firebase.
