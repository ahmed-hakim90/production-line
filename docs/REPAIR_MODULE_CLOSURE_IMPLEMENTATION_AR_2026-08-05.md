# تقرير تنفيذ إغلاق موديول الصيانة — 5 أغسطس 2026

## النتيجة التنفيذية

تم إغلاق مناطق الكود الست المحددة في خطة الإغلاق، مع فصل البيانات الفنية عن المالية، وحماية مصدر الأسعار، وإضافة دورة مستندية لفاتورة قطع الغيار، وتطوير تقرير الخزينة ومعاينة الجرد.

لا يتضمن هذا التقرير ادعاء نجاح UAT حي؛ لم تُنفذ معاملات على Firebase لأن بيانات اعتماد Admin وTenant اختبار معزول غير متاحة في جلسة التنفيذ. لم تُستخدم بيانات الإنتاج للاختبار.

## ما تم تنفيذه

### لوحة الصيانة حسب الدور

- `/repair` يوجه حساب الفني فقط إلى `/repair/technician` قبل تحميل لوحة تشغيلية أو مالية.
- الاستقبال يرى حالات التشغيل والإسناد والانتظار والإصلاح والجاهزية دون مؤشرات إيراد المركز.
- الإدارة ترى لوحة الإدارة من نفس الرابط، وتقرأ المؤشرات من `repair_job_financials` وأذونات الدفع المحمية.
- `/repair/admin-dashboard` أصبح رابط توافق يستخدم نفس موجه اللوحة.
- أزيلت حسابات `computeRepairJobCost` والحقول المالية القديمة من لوحة الاستقبال.

### كتالوج الخدمات المحمي

- أضيفت مجموعة `repair_service_catalog` المحمية وقواعد تمنع الفني من قراءتها.
- القراءة والكتابة الإدارية تتم عبر callable خادمي يزيد `revision` ويسجل التعديل.
- callable الفني يعيد الخدمة بالمعرف والاسم والتفعيل فقط بلا سعر.
- تجهيز إذن الدفع يقرأ السعر خادميًا ولا يقبل سعرًا من الواجهة.
- أضيف ترحيل Dry Run افتراضي للأسعار مع خيار التطبيق والتنظيف.

### موافقة العميل وإذن الدفع

- إذن الدفع يحفظ snapshot كاملًا لـ`serviceLines` و`partLines` داخل كل revision.
- رابط العميل مربوط بـ`authorizationId` و`revision` محددين وتوكنه مخزن كـhash.
- إصدار رابط جديد يبطل الرابط السابق، والقرار القديم أو المكرر يرفض داخل معاملة.
- صفحة العميل تعرض رقم الإذن والإصدار والإجمالي والخصم والصافي والبنود من نفس snapshot.
- أزيل مسار إنشاء رابط الموافقة القديم من خدمة الطلب.

### فاتورة بيع قطع الغيار

- الدورة: `draft` → `pending_discount_approval` → `ready_to_post` → `posted` → `cancelled`.
- الخادم يقبل `partId` والكمية فقط، ويقرأ الاسم والسعر من `Material.defaultSalePrice`؛ سعر المتصفح لا يدخل الحساب.
- السعر ظاهر للقراءة فقط في الواجهة، والتخفيض خصم مبلغ أو نسبة منفصل.
- يمنع مقدم الخصم من اعتماد خصمه.
- لا تتحرك الخزينة أو المخزون أو الحسابات قبل الترحيل.
- الترحيل يحدث داخل معاملة ويولد حركة المخزون، حركة الخزينة، وقيد الإيراد/الخصم/التكلفة/المخزون.
- الإلغاء متاح بعد الترحيل فقط، ويعيد المخزون ويولد حركة وقيدًا عكسيين دون حذف الأصل.
- الفاتورة تحفظ وسيلة الدفع ومركز التكلفة وحقول الضريبة الصفرية ومراجع الخزينة والقيد.
- الكتابة المباشرة على مجموعة الفواتير مقفولة بقواعد Firestore.

### الخزينة والتقرير

- حركات التحصيل والفواتير تحمل `paymentMethod`, `branchId`, `costCenterId`, `sourceId`, `journalEntryId`.
- التقرير يعرض رصيد أول الفترة والوارد والمنصرف والصافي وآخر الفترة.
- أضيف تجميع حسب الفرع ومركز التكلفة ونقدي/بطاقة/تحويل.
- أضيف كشف مطابقة يظهر الحركات الناقصة لوسيلة الدفع أو مركز التكلفة أو مرجع القيد.
- ملف Excel يحتوي أوراق الملخص واليومي والجلسات ووسائل الدفع والمطابقة.
- الطباعة وPDF تستخدمان نفس الفلاتر الظاهرة.
- الحركة اليدوية تتطلب سببًا ووسيلة دفع ومركز تكلفة مربوطًا بالفرع.

### معاينة الجرد

- رفع Excel/CSV أصبح مرحلة معاينة فقط ولا ينشئ جلسة.
- المعاينة تعرض الصفوف المعدودة، الفروقات، المتوقع، الفعلي، الأخطاء المانعة والتحذيرات.
- توجد إجراءات تنزيل الأخطاء وإلغاء المعاينة وإعادة الرفع.
- زر التأكيد يتعطل عند وجود خطأ مانع.
- إنشاء الجلسة تم نقله إلى callable خادمي يعيد قراءة أرصدة `stock_items` داخل معاملة؛ إذا تغير رصيد بعد المعاينة يرفض الإنشاء.
- قواعد Firestore تمنع إنشاء جلسة جرد مباشرة من العميل.
- اعتماد فروق الجرد يظل خطوة مستقلة؛ المعاينة أو الإنشاء لا يغيران المخزون.

### الحماية والترحيل

- الفني ممنوع من قراءة مجموعات الأسعار والماليات المحمية، وتُحجب قراءة `materials` عن حساب الفني غير الحاصل على صلاحية مخزون/تسعير إضافية.
- أضيفت مجموعات الكتالوج المحمي إلى نسخ Tenant الاحتياطية.
- ترحيل أسعار الخدمات: `npm run repair:services:migrate -- --tenant=TENANT_ID`، و`--apply --scrub` بعد الاعتماد.
- ترحيل ماليات الطلبات: `npm run repair:financials:migrate -- --tenant=TENANT_ID`، Dry Run افتراضي.
- ترحيل حالات الفواتير القديمة: `npm run repair:sales-invoices:migrate -- --tenant=TENANT_ID`، Dry Run افتراضي، ولا يخترع قيودًا أو خزينة تاريخية.

## ما يلزم قبل النشر النهائي

1. Backup للمجموعات المحددة على Tenant الاختبار.
2. نشر القواعد والفهارس والدوال الجديدة إلى مشروع الاختبار فقط.
3. تشغيل Dry Run للترحيلات الثلاثة وحفظ المخرجات.
4. تطبيق الترحيل على Tenant الاختبار بعد مراجعة الفروق.
5. تنفيذ سيناريو UAT الكامل بحساب استقبال وفني ومدير وخزينة وفرعين.
6. توثيق أرقام الإذن والإيصالات والفواتير والقيود والجرد ولقطات Network/Firestore.
7. بعد نجاح UAT فقط: تنفيذ نفس ترتيب النشر على الإنتاج مع نافذة رجوع ونسخة احتياطية.

## قرار التسليم

الكود والبناء والاختبارات الآلية جاهزة لمرحلة النشر التجريبي. التسليم التشغيلي النهائي يظل مشروطًا بـUAT حي على Tenant اختبار معزول؛ لا يجوز تجاوز هذا الشرط أو تنفيذ اختبار مالي داخل بيانات الإنتاج.
